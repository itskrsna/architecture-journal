# CLAUDE.md

Context for any future Claude Code session working in this repo. For the user-facing "how do
I use this" guide, see `README.md` instead — this file is the technical/decision record.

## What this is

An automated daily tech-article pipeline for the repo owner (Cloud/Solutions Architect —
Azure, .NET Core, Node.js/Python, DevOps). Drafts one article a day grounded in a real
experience note the owner logs, opens a GitHub PR for review, publishes approved ones to
dev.to. Built in a single extended Claude Code session on 2026-07-25.

## Execution architecture

Both halves run as **GitHub Actions workflows** — no GitHub connector of any kind, and no
metered Anthropic API billing:

1. **Drafting + opening the PR**: `.github/workflows/draft-article.yml`, triggered by a
   `push` to `main` that touches `config/experience-log.md` (i.e. whenever the owner pushes
   their daily entry), plus `workflow_dispatch` for manual test runs. The job runs
   [`anthropics/claude-code-action`](https://github.com/anthropics/claude-code-action) with
   the full daily-drafting prompt inlined in the workflow file — Claude Code itself reads the
   config files, drafts, self-reviews, files the draft, and runs the git/`gh` commands via its
   own Bash tool calls, exactly as a human would.
2. **Reacting to the PR closing** (publish on merge, log feedback on reject):
   `.github/workflows/handle-review.yml`, triggered on `pull_request: closed`
   (`scripts/devto-publish.ts`, `scripts/handle-pr-close.ts`) — unchanged.

**Authentication, two independent pieces:**
- Claude Code itself authenticates via `CLAUDE_CODE_OAUTH_TOKEN` (repo secret), a long-lived
  token generated by running `claude setup-token` locally and authenticating with the owner's
  own Claude subscription. This draws from that subscription's usage allowance — **no separate
  per-token billing**. The token is tied to whoever ran `setup-token`; it is not shareable
  org-wide, which is irrelevant here since this is a single-owner personal repo.
- Git/PR operations (branch, commit, push, `gh pr create`) use the job's own `GITHUB_TOKEN`,
  the same mechanism `handle-review.yml` already relies on — no PAT, no linked connector.

**Known rough edge:** `claude-code-action`'s docs are written mainly around its more common
PR-comment/issue trigger; the plain `push` trigger used here is less documented. Before
trusting the schedule, fire it once via the **Actions** tab → "Draft daily article" →
**Run workflow** (`workflow_dispatch`) and check the log for tool-permission or actor-check
rejections. If it fails outright, the most likely fix is broadening `claude_args`'
`--allowedTools` list or checking whether the action's bot-actor check needs an `allowed_bots`
entry for how this push is authored.

### History — how this pipeline's drafting step got here

This drafting step has changed shape twice since the pipeline was built on 2026-07-25:

1. **Originally**, drafting ran as a **Claude Code cloud routine** (trigger id
   `trig_01JS86HJCYYUFuB7T9UEvqGP`), authenticating git access via a fine-grained PAT embedded
   in its own stored prompt (GitHub connection for cloud routines was gated behind org-admin
   approval the owner didn't have). This worked for about a week, then broke: a proxy change
   on Claude Code's side started requiring cloud sessions to authenticate GitHub access
   through a linked connector regardless of any embedded credential, and this workspace never
   had one — nor could the owner get one approved.
2. **Briefly**, drafting moved to a GitHub Action that called the Anthropic API directly with
   a metered `ANTHROPIC_API_KEY` (~$10-25/month). This fixed the git-access problem
   (Actions has native `GITHUB_TOKEN` access, no connector needed) but the owner couldn't
   justify the ongoing API spend for a personal project.
3. **Current**: the GitHub Action still handles git access the same way, but Claude Code runs
   *inside* the Action (via `claude-code-action`) authenticated with a subscription OAuth
   token instead of a metered key — same zero-connector git access, zero extra billing.
   **The old cloud routine (step 1) should be disabled** — it can't push anyway, but leaving
   it enabled risks a duplicate/conflicting draft if GitHub connectors ever become available
   on this account — disable or delete it via the Claude Code web UI or the `schedule` skill.

## The hard gate (deliberate, not a bug)

The drafting prompt's first step checks `config/experience-log.md`'s `## Unused` section for
a bullet dated with the current date. If none exists, it stops immediately — no topic popped
from `topics-queue.json`, no draft, no PR, just a "Skipped" report. This exists because the
first real draft scored 81% on an AI-detection tool; the root cause was generic prose from
having no real specifics to ground the article in. Forcing a same-day experience-log entry is
the fix. Do not remove this gate without addressing that root cause some other way.

## Conventions

- Draft files: `drafts/<review_id>.md`, where `review_id` = `<YYYY-MM-DD>-<kebab-slug>`.
  Branch name is always `draft/<review_id>`; the workflow derives `review_id` by stripping
  the `draft/` prefix from the branch name, so don't change this pattern without updating
  `handle-pr-close.ts`'s `HEAD_REF` parsing.
- Front-matter schema (`title`, `pillar`, `tags`, `review_id`, `date`) is documented in
  `profile.md`'s "Draft file format" section and parsed by `gray-matter` in
  `scripts/devto-publish.ts`. Keep the two in sync if either changes.
- Automated commits (from both Actions workflows) use a bot identity
  (`architecture-journal-bot` / `articles-bot@users.noreply.github.com`), not the repo owner's
  personal identity.
- **This repo's local git identity is intentionally `imwebruster@gmail.com`**, not whatever
  the machine's global git config says (which is a work address) — set as a repo-local
  override. Do not let a global config leak back in; check `git config user.email` (no
  `--global`) before committing here if anything looks off.
- `topics-queue.json`'s `used`/`rejected` arrays are populated only by
  `scripts/handle-pr-close.ts` (on PR merge/close), never by the drafting workflow directly —
  it only ever pops from `queue` and appends to `experience-log.md`'s `Referenced` section.
  Rejected-PR metadata is fetched from the GitHub Contents API at the PR's head SHA (not from
  the working tree), because a rejected draft's file never reaches `main`.

## Known trade-offs / things to revisit

- **Redundant trigger, harmless**: merging a draft's PR brings that PR's own
  `experience-log.md` edit (today's entry moved to `## Referenced`) into `main`, which matches
  `draft-article.yml`'s path filter and fires it again immediately after every merge. The hard
  gate makes this cheap (it just exits at step 0 unless there happens to be another same-day
  entry), but it's a known inefficiency, not a deliberate design choice. Fixing it properly
  would mean distinguishing "human pushed a new entry" from "a merge brought entry-move diffs
  into main" — not worth the complexity for a personal project.
- `DEVTO_LIVE` (Actions repo variable) is `false` — merges currently publish as **private**
  dev.to drafts, not public. Flip to `true` once satisfied with quality.
- No paid plagiarism/AI-detection API is used, by the owner's choice — originality relies on
  grounding in `experience-log.md`, a banned-phrase self-review, a dedicated AI-detector
  self-check pass, and a lightweight web-search spot-check on distinctive sentences.
- Hashnode/Substack/Medium/LinkedIn are explicitly out of scope for automation (API access is
  either paid+gated, nonexistent, or closed — see the plan history for the research behind
  this). dev.to is the sole automated target.
